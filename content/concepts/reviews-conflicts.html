Concepts · Reviews & Conflicts

Findings, then a truthful conflict story.

Switchyard separates what Git can tell you from what Switchyard can tell you — and it is careful not to conflate them.

Review findings

Reviews produce structured, machine-actionable findings: severity, message, and file. Findings are durable and drive the editor gutters and the Needs Attention list.

Textual conflicts

Textual / Git merge conflict — overlapping edits to the same lines or files — is detected during preview integration (git merge on a scratch clone). The conflict-resolver performs a real three-way merge (git merge-file) onto the source branch; re-preview is then clean; integration proceeds. This is ordinary merge-conflict handling, done well.

Semantic conflicts

The more interesting case: Git says the combined tree is fine, but Switchyard knows the two pieces of work are incompatible. A repository can declare a deterministic contract (switchyard.contract.json); after a clean preview merge, Switchyard validates the contract against the merged tree: 

{ "rules": [
    { "kind": "field_equals",
      "a": "api/version.json:version",
      "b": "consumers/consumer.json:requires_version" }
] }

Attempt A moves the API and its consumer to v2 together (contract holds, integrates). Attempt B adds a new consumer file requiring v3 — a different file, so git merge is clean — but the merged tree violates the contract. Switchyard reports a semantic error finding, parks the attempt, and blocks the Integration Queue. No LLM is involved; it is deterministic contract validation on the preview-merged tree.

Precise language The two mechanisms are deliberately distinct. "Git reports a conflict" and "Switchyard knows the pieces are incompatible" are different claims, and both are proven separately.
