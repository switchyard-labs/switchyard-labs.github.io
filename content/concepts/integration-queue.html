Concepts · Integration Queue

Canonical only moves through the queue.

Strict ordering, policy gates, compare-and-swap, and a repair loop — so concurrent work lands predictably, never as a last-writer-wins race.

The rules

PropertyBehaviour
OrderingStrict FIFO — at most one integration in flight. A later PR that edits the same file previews against the earlier PR's result.
PolicyIntegrates only when the check passed AND preview is clean AND (for high-risk work) approval has been given.
FreshnessIntegration is CAS-guarded; a moved base is re-queued with bounded attempts.
Repair loopPreview conflicts block the item and route the attempt to the conflict-resolver; a fix re-queues it.
Risk classesLow / medium / high from change scope; risk drives policy escalation.

Why strict FIFO matters

Without ordering, two items that edit the same file would both preview against the old canonical and one would conflict at merge time. With strict FIFO, the second item previews against the first item's integration — so conflicts are detected and routed to the repair loop instead of surfacing as a merge failure. This was demonstrated with same-file contention: the first PR integrated, the second was blocked by preview, resolved by the repair loop, re-queued, and integrated.

Measured, not guessed

The queue was exercised under churn and measured:

  • 3 clean PRs integrate in order (~18–22 s wall).
  • 10 PRs, full queue-to-done ~42 s (~4.2 s/item).

The dominant cost is a scratch clone per operation (preview + merge). A cached bare-mirror + worktree model is the next optimization target.
